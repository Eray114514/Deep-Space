# 深空的模型协作约定

**[2026-11-12 用户决策] 主控由 Codex 交给 Claude。** Claude 亲自完成大部分工作，包括高难度算法、shader、渲染架构、视觉标杆和集成，自己只做极简验收。独立验收交给 Codex。Carbon（Gemini）继续可用，由 Claude 派发。派发按已授权的工作范围、下列分工和 `cross-agent` 技能（`C:\Users\Eray0\.agents\skills\cross-agent\SKILL.md`）执行。交接背景见 [Codex → Claude 主控交接](reviews/handover-codex-to-claude-2026-11-12.md)。

其他文档里此前写下的分工按这条读：「Codex 主责 / 负责 / 集成」读作 Claude 实现、Codex 验收；「交 Fable」即主控自己做；「Codex 独立验收 / 复核」不变。

## 三方分工

| 角色 | 模型与档位 | 负责 |
|---|---|---|
| 主控 | Claude（Claude Code，Fable 5.2） | 界定范围、实现、集成、文档与任务表同步、派发与收回、向用户汇报。自己只做任务所需的最小验收 |
| 验收 | Codex CLI，`gpt-6.1-sol`，`high` | 独立复核差异，按需要完成数值、浏览器、GPU、连续画面与性能回归，给出通过或问题清单 |
| 分担 | Carbon，`gemini-4-carbon`，`high`（经 `dshx`） | 主控选择交出去的难任务：与前端效果关系不大的，或难点主要在工作量大、耗时长的 |
| 最终确认 | 用户 | 审美、实机多设备体验、范围与方向决策 |

- 不回环派发。Codex 做验收时不再调用 Claude，Carbon 同理。
- 默认在《深空》主目录工作。**不另开文件夹或工作树**，确实需要隔离时先问用户（见交接说明里的遗留目录）。
- 并行修改用清晰分开的文件范围。主控保存每次派发返回的会话 ID、对应任务和提交范围。

## 主控的极简验收

主控交付前只做证明「改动能跑」的最小检查：`npm test`（宇宙锁暂缓期间，以锁之前的各项通过为准），以及改动直接涉及的一条针对性命令或一次打开确认。完整回归矩阵、多轮复审、截图批次和性能取证交给 Codex。交付说明列出改动路径、实际做过的最小验收及结果、已知问题和未验证的假设，让验收方知道从哪里查起。

## 如何调用 Codex 验收

- 模型和档位与 `~/.codex/config.toml` 的默认一致，仍显式写出：

  ```sh
  codex exec --json -m gpt-6.1-sol -c model_reasoning_effort=high --dangerously-bypass-approvals-and-sandbox "TASK"
  ```

  从《深空》主目录运行。保存 `thread.started` 里的 `thread_id`，读最终回复和退出码。接续用 `codex exec --dangerously-bypass-approvals-and-sandbox resume SESSION_ID "FOLLOW_UP"`。多行提示词不要直接当命令行参数传，按已安装版本的 `codex exec --help` 用文件或标准输入。
- 验收任务另开新会话。原主控会话 `01a0fd3e-b2f7-7a40-a953-0a2a03c665a6` 体积很大，只作历史记录查阅，不作为验收会话接续。同一批改动的复验接续该批的验收会话。
- 给 Codex 的说明包括：交付目标、提交或差异范围、相关代码路径、主控已做的最小验收、已知问题、希望重点怀疑的地方。视觉任务附目标画面。**不指定结论**，也不替它规定验收步骤，由它自行决定验证方式和深度。
- Codex 可以为验收写临时脚本和跑测试。修复由主控来做；Codex 发现问题时返回证据和定位，除非主控在该次派发里明确请它顺手修。
- 验收结论是报告，不是事实。主控对照差异和证据核对后，再向用户报告通过。

## 如何使用 Carbon

- 经 `dshx` 驱动 DSH 桌面端，默认 **Gemini 4 Carbon（`gemini-4-carbon`），High**，不改模型和档位。桌面端须在运行，先 `dshx --status`。必须显式选 `--mode standard` 或 `--mode ptc`。多行任务写成 UTF-8 文件，用 `--task-file` 传入。`--cwd` 指向《深空》主目录。
- **攻关首先是主控自己的事。** Carbon 的能力只比 Claude 略弱一点，区别在额度多。交给它是为了省主控的额度和时间，不是因为主控做不了。
- 适合交给 Carbon 的两类：与前端效果关系不大的难任务；难点主要在工作量大、耗时长的任务，例如需要长时间实测的冷启动、GPU 性能、数值与资源生命周期。可以一次交较大的任务量并让它自设目标。
- Carbon 速度慢，`429` 重试等待属正常，不要因为日志安静就终止。
- Carbon 可以承担工程型前端实现，审美发挥弱于 Claude。决定玩家所见的画面风格和标杆、以及最难的开放性问题，由主控自己做。
- 给 Carbon 正常的任务说明，包括目标、事实、范围和产品约束。它自行决定验证方式和深度。交付后由 Codex 独立验收，主控合入。

## 派发、交付与接续

**把 Codex 和 Carbon 当作平等的合作者。** 分工代表各自对交付负责，没有上下级指挥关系。说明用户想要的结果、已验证的事实，以及预算、接口、修改范围等必要约束，给对方充分空间自行判断。主控的想法如果能帮助交接，就作为可供挑战的背景提供。验收意见以交付和证据为依据，主控不同意时给出反证，分歧交用户裁决。

授权范围内的后续任务与上一会话的代码范围、场景、目标和关键证据基本重叠时，优先接续同一个模型的已保存会话。只补新的反馈、提交和约束。上下文已实质变化或上一会话状态不明时，开新会话并提供简短的已验证交接。

遇到 CLI 不可用、登录失效或额度限制时报告实际情况，由用户决定是否改派，不静默换路径。
